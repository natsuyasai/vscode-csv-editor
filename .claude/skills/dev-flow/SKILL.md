# アプリ開発標準フロー（dev-flow）

このプロジェクトでアプリ開発を行う際の **標準フロー** を定義します。メインエージェントはこのフローに従って全体を管理し、各フェーズで対応するスキルを呼び出します。実装作業はサブエージェントへ委譲し、メインエージェントは常に **レビューと全体管理** に徹します。

## フロー全体像

```
[1] 要求明確化        → /clarify-requirements
        ↓
[2] 実装プラン策定     → /plan        （複数案は確認 / .tmp/plans/ に引き継ぎ文書を出力）
        ↓  (ユーザー承認)
[3] ブランチ作成→実装  → /implement   （サブエージェント委譲 + TDD + 多層テスト + 作業毎コミット）
        ↓
[4] プロパティベーステスト → /property-test （仕様が明確かつ実装上可能な場合のみ）
        ↓
[5] 最終チェック       → /check-creation （format / test / typecheck / lint / build）

[横断] 同じ指摘が複数回出たら → CLAUDE.md に追記（「開発原則」参照）
```

各フェーズの詳細は対応スキルに委ねる。このスキルは **順序・移行条件・全体管理の責務** を定義する。

---

## フェーズ詳細

### [1] 要求内容を明確にする — `/clarify-requirements`

- ユーザーの要求の背景・目的・受け入れ条件を確認し、曖昧さを解消する。
- 不明点・仕様の疑問があれば **作業を中断して質問する**（CLAUDE.md 開発原則）。
- アウトプット: 明確化された要求（箇条書きの受け入れ条件）。

**移行条件**: 受け入れ条件が確定し、ユーザーが合意したら [2] へ。

### [2] 実装プランを策定する — `/plan`

- 明確化した要求を元に実装プランを策定する。
- **複数案がある場合は、どの案で進めるかを必ずユーザーに確認する**（AskUserQuestion 等）。
- 作業を **別セッションにも引き継げるよう、一時ドキュメントとして** `.tmp/plans/<feature>.md` に出力する（`.tmp/` は gitignore 済み）。
- アウトプット: 承認済みプラン文書（`.tmp/plans/<feature>.md`）。

**移行条件**: 対応方針が確定し、ユーザーが実装開始を承認したら [3] へ。

### [3] 実装作業 — `/implement`

実装を開始できる状態になったら作業を開始する。

- まず **作業用ブランチを作成** する。
- **実装はサブエージェントに委譲** し、メインエージェントはレビューと全体管理を行う（サブエージェントの成果物を必ずレビューしてから取り込む）。
- 実装は必ず **t-wada 推奨の TDD**（Red→Green→Refactor）で進める（`/tdd` を参照）。
- 以下の **多層テスト** を作成する:
  1. **vitest による単体テスト**（hooks / stores / utilities / 純ロジック）: `src/.../<Name>.spec.ts(x)`
  2. **Storybook によるコンポーネントカタログ**: `src/.../<Name>.stories.tsx`（各バリエーション・テーマ）
  3. **Storybook の play function による画面の単体テスト**: 各コンポーネント Story の `play` でインタラクション検証
  4. **機能の結合テスト**: アプリ全体 Story `src/App.<Feature>.stories.tsx` の `play`（複数コンポーネント連携）、および DOM 結合の `src/.../<Name>Integration.spec.tsx`
- UI 開発の前には必ず Storybook MCP を確認する（`/storybook-dev` 参照）。
- **作業（論理的なまとまり）毎にコミット** する。

**移行条件**: 要求の受け入れ条件をすべて満たす実装とテストが揃ったら [4] へ。

### [4] プロパティベーステスト — `/property-test`

- 実装完了後、**仕様が明確かつ対応コードの内容から実装可能** な場合にプロパティベーステストを作成する。
- 対象が判断できない/仕様が曖昧な場合は無理に作成せず、その旨を報告する。
- ファイル: `src/.../<Name>.property.spec.ts`（fast-check 使用）。

**移行条件**: PBT の追加可否を判断・対応したら [5] へ。

### [5] 最終チェック — `/check-creation`

- すべて完了したら **フォーマッターの適用・テスト実行・ビルド確認** を行う。
- ルートと `webview-ui` の両方で `format / check-types / lint / test` を実行し、エラー・警告ゼロにする。
- 加えて `webview-ui` で `npm run build` と `npm run build-storybook` が成功することを確認する。

## 横断ルール: 繰り返しの指摘は CLAUDE.md へ

- **全作業内で同様のミスの指摘が複数回（2回以上）発生した場合は、必ず `CLAUDE.md` に再発防止策を追記する。**
- 追記先は内容に応じて「開発原則」「開発手順」「機能実装詳細」等の適切なセクション。
- 追記は「何を・なぜ・どう防ぐか」を1〜数行で簡潔に記載する。

## メインエージェントの責務（全フェーズ共通）

- 各フェーズの移行条件を満たしているか確認してから次へ進む。
- サブエージェントへ委譲した実装は **必ずレビュー** し、品質・規約適合・テスト網羅を確認する。
- 疑問があれば中断して質問する（推測で進めない）。

## 関連スキル

- `/clarify-requirements` — [1] 要求明確化
- `/plan` — [2] プラン策定
- `/implement` — [3] 実装（サブエージェント委譲・TDD・多層テスト）
- `/tdd` — TDD の Red-Green-Refactor 詳細
- `/storybook-dev` — Storybook 駆動 UI 開発
- `/component-create` — コンポーネント雛形生成
- `/property-test` — [4] プロパティベーステスト
- `/check-creation` — [5] 最終品質チェック
- `/refactor` — Tidy First / Fowler 式リファクタリング
